STEP 46 — Temporal Corpus Scope

Goal

Add a temporal filtering control to DramaScope so that users can restrict the active corpus to a selected chronological range.

This should build directly on the multi-playwright infrastructure established in STEP 45/45A.

The purpose is to allow users to investigate language patterns within different chronological portions of the Early Modern drama corpus while preserving the existing analytical architecture.

This is a corpus-scope/filtering enhancement.

Do NOT introduce new analytical methods.

Keep this task targeted.

- Inspect only the files/components necessary to implement temporal corpus filtering.
- Reuse the shared filtering architecture established in STEP 45.
- Do not perform another broad investigation of the whole codebase.
- Do not repeatedly re-read unchanged sections of Analysis.tsx.
- Do not take screenshots unless required to diagnose a problem.
- Make the smallest coherent architectural change.
- Run one final TypeScript check after implementation.
- Do not spend time fixing pre-existing TypeScript errors unrelated to this step.

Existing Architecture to Preserve

DramaScope currently loads four source files into two logical datasets:

LINES:
- corpus_lines_real.csv
- early_modern_drama_lines.csv

SPEECHES:
- corpus_speeches_real.csv
- early_modern_drama_speeches.csv

The canonical schemas already contain:

- playwright
- year_est
- decade
- year_min
- year_max
- year_mid

Playwright filtering is implemented globally through UIContext.

The current analytical split must remain:

- Lexical → LINES
- Semantic → SPEECHES
- Discursive → SPEECHES

STEP 45A also introduced playwright-aware analytical cache identities.

Preserve all of this.

---

Temporal Filtering Principle

Use the existing year metadata as the basis of temporal filtering.

Do NOT classify rows primarily through historical-period labels such as:

- Elizabethan
- Jacobean
- Caroline

Those may be considered later as optional convenience presets.

For STEP 46, implement a transparent numerical year-range filter.

Use `year_est` as the primary temporal field because this is already the application's principal estimated-date field.

Do not change or reinterpret the existing date metadata.

---

1. Add Temporal Range to Shared UI State

Extend the existing UIContext/global filtering architecture with a temporal range.

Recommended conceptual state:

temporalRange:
- startYear
- endYear

Determine the minimum and maximum available `year_est` values dynamically from the loaded corpus rather than hard-coding them.

The default range must include the entire available corpus.

Therefore, when the application initially loads:

Temporal Range = earliest available year → latest available year

This means the default behaviour remains equivalent to having no temporal restriction.

---

2. Filtering Order

Extend the shared selected-dataset architecture established in STEP 45.

Conceptually:

merged corpus
→ selected playwrights
→ selected temporal range
→ existing corpus/play/genre/speaker filters
→ analytical functions

Both analytical datasets must respect the same temporal range:

selectedLines:
- selected playwrights
- selected year range

selectedSpeeches:
- selected playwrights
- selected year range

Do not implement separate temporal filtering independently inside Lexical, Semantic, and Discursive tabs.

The filtering should occur at the shared corpus-selection level wherever practical.

---

3. Date Inclusion Rule

Use `year_est` for inclusion.

A row should be included when:

startYear <= year_est <= endYear

The range must therefore be inclusive at both ends.

Do not use year_min/year_max to determine inclusion in STEP 46.

Do not silently substitute year_mid or decade.

If rows contain missing or invalid year_est values, identify how many exist before deciding how to handle them.

If there are no missing/invalid year_est values, no special handling is required.

If there are missing/invalid values, report this before introducing any non-trivial fallback rule.

4. Sidebar Control

Add a compact temporal control to the existing GLOBAL SCOPE area of the sidebar.

Recommended label:

DATE RANGE

The user should be able to specify:

To:   [year]

Use compact controls consistent with the existing DramaScope visual design.

The control must:

- prevent startYear from exceeding endYear;
- prevent values outside the available corpus range;
- allow the full corpus range to be restored easily.

Include a compact:

Reset

or equivalent control that restores the full available chronological range.

Do not change sidebar width.

Do not redesign unrelated sidebar controls.

Do not add historical-period preset buttons in this step.

---

5. Interaction with Playwright Selection

Temporal range and playwright selection must work together.

Examples:

Shakespeare + full date range
= all Shakespeare plays

Marlowe + 1585–1595
= Marlowe material whose year_est falls within 1585–1595

Shakespeare + Marlowe + 1590–1600
= material from both playwrights within that date range

All playwrights + 1600–1620
= all included playwrights represented within 1600–1620

The selected temporal range should NOT automatically change merely because the user selects a different playwright.

For example:

If the user selects 1590–1600 and then switches from Shakespeare to Marlowe, preserve 1590–1600.

Do not silently reset the temporal range.

Do not retain an individual play that is no longer part of the active corpus.

13. Existing Time Granularity

IMPORTANT:

Do not confuse Temporal Range with the existing Time Granularity control.

They have different purposes:

Temporal Range
= which chronological portion of the corpus is included

Time Granularity
= how temporal results are grouped/displayed within that corpus

Therefore:

DATE RANGE: 1590–1610
TIME GRANULARITY: Year

means analyse material dated 1590–1610 and display temporal patterns by year.

DATE RANGE: 1590–1610
TIME GRANULARITY: Decade

means analyse the same material but group temporal outputs by decade.

Preserve the existing Year/Decade functionality exactly.
